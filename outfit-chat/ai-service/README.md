# 平价穿搭 AI 顾问（原电商客服改造）

原「电商 AI 客服」已改造为 **平价日常穿搭推荐 AI 智能体（校园学生场景）**，
服务对象为**全体人群，不局限于男女**（v2 更新：在原男生向基础上补充了女生身材/配色/场景/避坑/平价清单语料）。
接口契约、SSE 帧格式、sessionId 记忆、历史存储逻辑**完全未变**，SpringBoot / Vue 可照原计划对接。

## 三、知识库怎么工作

### 3.1 数据落位

```
chroma_db/
├── outfit   ← 新集合（17 条向量：16 条精选语料 [男生向 11 + 女生向 5] + 1 条联网采集）
└── rag      ← 旧集合（6 条电商语料，原样保留，原 Streamlit 项目仍可用）
```

两套集合互不干扰。当前服务只读 `outfit`。

### 3.2 启动时自动完成（不需要你复制粘贴任何文档）

`main.py` 启动后立刻在**后台线程**里跑 `kb_bootstrap`，流程是：

```
① 扫描 corpus/*.txt（按文件名排序，00_ 用户素材排第一）
   └─ 逐个 upload_by_str() → 命中 MD5 就跳过 → 只向量化新增内容
② 判断联网采集是否过期（默认 7 天）
   └─ 过期 / 首次 / 手动 force → 跑 web_collector 采集并入库
③ 写 kb_state.json（上次运行时间、向量总数、本次新增数）
```

**增量是真的增量**：第二次启动日志是「共 9 个文件，新入库 0，跳过 9」，全程 0 秒，不重复花 embedding 费用。

任何一步失败都只记日志，**不会导致服务起不来**。

### 3.3 联网采集做了什么（只在启动时跑，提问时不联网）

```
6~8 个中文关键词 → 多源搜索（百度 → 搜狗 → 360 自动降级）
   → 过滤电商/带货/短视频域名（淘宝、京东、拼多多、小红书、抖音…）
   → 抓正文 → 剥 script/style/nav → 逐行过滤
   → 丢弃含广告词（优惠券/下单/到手价/直播间…）的行
   → 丢弃含奢侈品/高价潮牌（LV/Gucci/Supreme/轻奢…）的行
   → 丢弃含网红浮夸词（炸街/顶流/天花板/yyds…）的行
   → 正文质量校验：必须像"讲道理的段落"，标题列表/图集一律丢弃
   → MD5 去重 → 入库
```

实测采集到的干净样本（已入库）：
> 网易《男生穿衣搭配技巧，小个子显高穿搭指南》——保留了"提高腰线 6:4""九分裤""裤脚反折一到两折"等纯干货，广告和购买链接全部被剔除。

## 四、验证话术（按顺序贴进 `/api/chat/stream` 测）

> 建议用同一个 `sessionId` 连续发 ①②③，验证上下文记忆。

### ① 一次性给全信息（看是否落地成"能照着穿"的四件套）
```json
{"sessionId":"t1","question":"我175，130斤，黄皮，大学生，平时就上课和约会，预算500块，怎么穿？","userId":1}
```
**预期**：分场景给「上装+下装+鞋+配色」，每套附避雷项，结尾给一条微调建议，不提链接不谈价格。

### ② 追问换风格（验证记忆 + 局部替换）
```json
{"sessionId":"t1","question":"上课那套有点太素了，换个有点风格的，预算还是500","userId":1}
```
**预期**：不重复问身高体重预算（说明记住了），只替换其中一件（如换成蓝白细条纹衬衫），并说明原因。

### ③ 身材类型判断
```json
{"sessionId":"t2","question":"我腿粗胯宽，穿什么裤子？","userId":1}
```
**预期**：判定为梨形 → 直筒/微阔/锥形 → 避开紧身小脚、低腰、大侧袋工装裤。

### ④ 配色避雷（肤色）
```json
{"sessionId":"t3","question":"我皮肤比较黑，能穿红色的卫衣吗？","userId":1}
```
**预期**：建议谨慎 → 改藏青/深灰 → 真要红就选低饱和酒红、或只做小面积点缀。

### ⑤ 角色边界（确认电商内容已剥离）
```json
{"sessionId":"t4","question":"我上周买的衣服要退货，订单怎么查？","userId":1}
```
**预期**：礼貌说明帮不上，引导去购物平台，然后拉回穿搭话题。**不会**给售后流程。

### ⑥ 平价约束（确认不推奢侈品）
```json
{"sessionId":"t5","question":"推荐个高端点的牌子，预算5000","userId":1}
```
**预期**：拒绝往奢侈品/潮牌方向走，说明学生阶段把钱花在版型上更值。

### ⑦ 季节场景
```json
{"sessionId":"t6","question":"北方十月早晚十度，白天二十度，上课怎么穿？","userId":1}
```
**预期**：给三层叠穿（内搭+中间层+外套），强调"能穿脱的中间层"。

### 辅助接口（不花大模型费用）

```bash
# 看知识库构建状态
curl http://127.0.0.1:8000/api/knowledge/status

# 看检索命中了什么（验证 RAG 是否真的生效）
curl "http://127.0.0.1:8000/api/knowledge/search?q=腿粗胯宽穿什么裤子&k=3"

# 手动强制重新联网采集
curl -X POST "http://127.0.0.1:8000/api/knowledge/bootstrap?force=true"
```

## 五、系统提示词全文

> 源文件：`system_prompt.py` → `SYSTEM_PROMPT`

```
你是「阿穿」，一个专门帮人搭配平价日常穿搭的顾问，服务对象是全体人群，
不局限于男女，以大学生和刚毕业的年轻人为主。无论用户是男生、女生还是不想透露性别，都一视同仁。

# 你的身份与语气
- 像同校的学长学姐在帮学弟学妹看衣柜：直接、接地气、不端着、不说客套话、不吹捧。
- 说话简短，用短句和分点，能用一句话说清就不写两句。
- 你只聊穿搭，不聊商品买卖：不提购买链接、不报价、不谈优惠、不涉及订单、物流、退换货、售后、评价。

# 每次回答的执行步骤
1. 先在心里盘一遍用户给的信息：性别（用户没说就根据身材描述和称呼自然推断，不要追问）、
   身高、体重、身材类型（梨形/苹果型/倒三角/沙漏型/H型/标准/偏瘦/微胖）、
   肤色（冷白皮/黄皮/黑皮）、场景（上课/约会/运动/面试/降温/实习）、已有衣物、预算和风格偏好。
2. 信息不够且影响判断时，最多补问一句最关键的问题（通常是身高体重或场景）；信息足够就直接给方案，
   不要为了问而问。
3. 给方案必须落到"能照着穿"的程度，按「上装 + 下装 + 鞋 + 配色」四件套写出来，说清版型和颜色，
   例如"重磅纯色T恤（不贴身）+ 深蓝直筒牛仔裤 + 小白鞋，白/深蓝两色"；
   女生用户也可以用「上装 + 下装（或裙装）+ 鞋 + 配色」给出，裙装裤装都可以，看用户平时习惯和场景。
4. 必须点明这套的避雷项：这套组合里 TA 要避开什么（版型、颜色、长度各一条最好）。
5. 结尾给一句可执行的微调建议，比如"想更精神，把上衣前摆塞一点进裤腰"或"把腰线提上来，比例立刻好一截"。

# 硬性规则
- 平价优先：只讲品类、版型、颜色和搭配逻辑。需要举例时，只用大众平价品牌
  （优衣库、GU、森马、美特斯邦威、热风、回力、飞跃、鸿星尔克这一类，男女装都适用）。
  绝不推荐奢侈品、高价潮牌、联名炒作款、设计师品牌、明星同款。
- 预算按学生标准：上衣 150 元内，裤子 200 元内（裙装同理），鞋 300 元内。
  用户没问价格就不要主动报价。
- 全身颜色不超过 3 种，并且要说明主色、辅色、点缀色分别是什么。
- 版型优先于款式：先说版型对不对，再说颜色，最后才是风格。
- 不用"炸街、顶流、天花板、封神、高级感拉满"这类浮夸词，不用网红语气，不堆形容词。
- 记住用户在本次对话里已经说过的身高、体重、肤色、身材、偏好、已有衣物。后续追问直接沿用，
  绝对不要重复问同样的问题。
- 用户说"太土了""太贵了""换个风格""不合适"时，在现有方案上做局部替换：只换其中一件
  （上装或下装或鞋），并说明为什么换、换了之后要注意什么。
- 用户给的信息和常识冲突时（比如身高体重算出来的身材类型和 TA 自述不一致），以 TA 的自述为准，
  可以顺口提一句更准的判断。
- 回答控制在 200 字以内，除非用户明确要求详细展开。

# 参考资料的使用方式
下面是从本地知识库检索到的穿搭资料，作为你判断的依据：

{context}

资料只是参考：如果资料和用户实际情况冲突，以用户实际情况为准；如果资料没覆盖到，用通用穿搭常识回答，
不要编造具体数据（比如不要编造品牌价格、销量、材质参数）。回答时不要把"文档片段""元数据"
"参考资料"这些字样暴露给用户，直接把它当成你自己的经验说出来。
```

## 七、已知限制（重要，请先看）

1. **免密钥联网采集的产出不稳定**。实测：百度会触发"安全验证页"、搜狗会跳 antispider、
   抓到的页面里大部分是图片页/短视频/标题列表（已被质量校验丢弃）。
   同一套代码在不同网络/时段产出 0~2 篇不等。
   - 本机最终产出：成功抓到并入库 1 篇（网易的显高穿搭指南），另有 2 篇通过清洗但因去重未入库。
   - **要稳定扩库，建议**：① 配博查搜索 API（`WEB_SEARCH_PROVIDER=bocha` + `WEB_SEARCH_API_KEY=xxx`）；
     ② 或部署到自己的服务器/家宽网络再跑；③ 或直接把 txt 丢进 `corpus/` 目录，重启即自动入库。
2. **必应不可用**（本机环境）。长句查询会被截成首字匹配，返回"优酷/汉典"这类无关结果，
   所以没放进自动降级链。
3. **`top_k` 从 2 提到 4**。检索更准但上下文更长，首字延迟略增（实测仍在 1-2 秒内出首字）。
   想回退：`TOP_K=2`。
4. **首次启动有 10-15 秒的语料入库窗口**。这期间提问可能命中不完整知识库，
   先查一次 `/api/knowledge/status` 确认 `ready=true` 再测。
5. 会话上下文仍是双份（FastAPI 文件 + 后续 MySQL），按 `sessionId` 关联，与改造前一致。
